# ProjectSetupWizard

Claude Code と Codex で進める個人開発の案件に、AI の運用ルール一式 (役割、承認、課題、検証、再開の手順) を生成・更新するツールです。Node 22 の標準ライブラリだけで動き、追加の依存はありません。

> A small CLI plus Claude Code skills that generate and maintain AI-collaboration documents (roles, approval rules, tasks, validation, session start prompts) for a project. Documents, prompts and CLI messages are in Japanese. Node 22 standard library only. MIT licensed.
>
> **Japanese only.** This tool is written for use in Japanese: the generated documents, the skill instructions, the questions and the CLI messages are all Japanese. It has not been tested in English or any other language, and there is no English template.

## 何をするか

案件フォルダに、次の文書を作ります。このルール一式を「ウィザード標準」と呼びます。

| 文書 | 役割 |
| --- | --- |
| `CLAUDE.md` / `AGENTS.md` | 各 AI の短い入口。役割と、いつ何を読むか |
| `WORKFLOW.md` | 正本。役割、編集してよい範囲、承認の決まり、進め方 |
| `PROJECT.md` | 目的、MVP、対象外など (入力をそのまま引用で保存) |
| `TASKS.md` | 初期確認、課題と合格条件、再開メモ |
| `VALIDATION.md` | 検証コマンドの候補、実在を確認した検証レシピ、結果の記録 |
| `START.md` | 最初のセッションに貼る開始文 |
| `RULES.md` | 案件固有のルール (あるときだけ) |
| `setup.config.json` / `generated.manifest.json` | 設定と、生成・更新の記録 (実行履歴) |

役割分担は 4 つのモードから選びます。

| モード | 主導・レビュー | 実装 |
| --- | --- | --- |
| `codex-led` | Codex | Claude |
| `claude-led` | Claude | Codex |
| `codex-solo` | Codex (独立レビューなし) | Codex |
| `claude-solo` | Claude (独立レビューなし) | Claude |

## 前提

- Node.js 22 以上
- Claude Code か Codex (Skill を使う場合)。CLI だけなら不要です。

## 使い方 (Claude Code / Codex の Skill)

1. このリポジトリを clone します。
2. **このフォルダで** Claude Code か Codex を開きます。
3. 次のコマンドを打ちます。対象の案件フォルダは、質問のなかでパスを指定します。

| Claude Code | Codex | すること |
| --- | --- | --- |
| `/project-new` | `$project-new` | 新しい案件の文書を、質問に答えて生成する |
| `/project-change` | `$project-change` | 既存の案件を更新する。ウィザードなしで作った案件に導入する |
| `/project-audit` | `$project-audit` | 案件の文書を診断する (読むだけ) |
| `/project-update` | `$project-update` | このツール自体の更新を提案する |

細かい選択が続く場面では、「おすすめで」とまとめて進める近道があります (案件名・モード・出力先・承認は、必ず本人が選びます)。

どちらの AI でも同じ手順で動きます。手順の本体は `.claude/skills/` に 1 つだけあり、Codex 用の `.agents/skills/` はそれを読むよう案内する短い入口です。質問は、どちらのAIでも利用可能な質問ウィンドウで出し、使えない場合は同じ選択肢を番号付きで会話に出します。複数選択に非対応なら採否を個別に聞きます。Codex では `/skills` から選ぶこともできます。

どのコマンドも、書き込む前に内容を見せて確認を取ります。

### `/project-new` で聞かれること

質問は 4 回ほどに分けて出ます。選択肢から選ぶか、自由に書きます。事前に考えておくとよいのは **案件名・目的・MVP・モード** の 4 つで、ほかは「未定」や「おすすめで」でかまいません。

| 回 | 聞かれること | 選択肢の例 | 用意しておくもの |
| --- | --- | --- | --- |
| 1 | 案件名 | (自由記述) | **要る** |
| 1 | 目的 | 自分用のツール / 学習・動作検証 / 公開サービスの試作 | **要る** (分類を選ぶだけでもよい) |
| 1 | モード | `claude-led` / `codex-led` / `claude-solo` / `codex-solo` | **要る** (どちらの AI に主導させるか) |
| 1 | 技術 | Node.js / Python / Web フロントエンド / 未定 | 未定でよい |
| 1 | 運用の段階 | 最小 / 標準 (おすすめ) / しっかり | おすすめでよい |
| 2 | MVP | 1 回目の答えに合わせた候補が 2〜3 個出る | **要る** (「最初に動けば成功」と言える範囲) |
| 2 | 引継ぎ、段階、対象外 | 開始文を貼る / MVP → 改善 → 公開準備 / 課金・決済 など | おすすめでよい |
| 2 | push の承認 | 毎回承認 (おすすめ) / 作業ブランチへは承認なし | おすすめでよい |
| 3 | 別 AI の起動 (協働モードだけ) | 主導担当が範囲内で起動してよい (おすすめ) / 毎回承認 | おすすめでよい |
| 3 | 各 AI のモデル・effort | いまの設定のまま / 既定 / 指定 | 既定でよい |
| 3 | 画面のある案件か | 入れる / 入れない | 目的と技術から分かれば確認だけ |
| 4 | 検証コマンド、編集してよい場所、禁止事項 | `npm test` / `src/` / 依存の追加 など | 未定でよい |
| 4 | 出力先フォルダ | このフォルダの隣の `<案件名>` など | **要る** (空か、まだないフォルダ) |

1 回目のあとに「残りをおすすめでまとめて決める / 1 つずつ選ぶ」を聞かれます。おすすめで決めても、案件名・目的・MVP・モード・モデル・出力先は必ず本人が選びます。

答え終わると要約が出て、「この内容で設定を保存してよいか」「この digest で生成してよいか」を順に確かめます。承認するまで何も書き出しません。

### やり取りの例

読書メモの小さな Web ツールを、Claude 主導で始める場合の例です (流れを示すための例で、実際のセッションの記録ではありません)。

```text
あなた: /project-new

1 回目  案件名: ReadingLog          目的: 自分用のツール
        モード: claude-led          技術: Web フロントエンド
        運用の段階: 標準 (おすすめ)
        → 「残りはおすすめで」を選ぶ
2 回目  MVP: 本の題名と感想を 1 件登録して、一覧で見られる (候補から選ぶ)
3 回目  別 AI の起動: 主導担当が範囲内で起動してよい (おすすめ)
        モデル: 両方とも既定      画面のある案件: 入れる
4 回目  出力先: ../ReadingLog

AI: 要約を表示 → あなた: 保存してよい
AI: 生成予定のファイルと digest を表示 → あなた: 生成してよい
```

生成前に表示される内容 (`plan`) は次のとおりです。

```text
mode: claude-led  handoff: manual  profile: standard  push: 毎回承認  別AIの起動: 主導担当が範囲内で起動してよい  画面の決まり: 入れる
files:
  - initial-settings/setup.config.json
  - docs/PROJECT.md、docs/WORKFLOW.md、docs/TASKS.md、docs/VALIDATION.md、docs/CONTEXT.md、docs/USER_TESTS.md、docs/START.md
  - CLAUDE.md、AGENTS.md
ないときだけ作る: .gitignore
未定 (生成は可): permissions.allowedPaths
```

生成後は、`docs/START.md` の開始文を各 AI に貼って最初のセッションを始めます。最初のセッションでは、未定にした項目 (この例では編集してよい場所) を、案件側の AI が初期確認 (T-000) でまとめて聞きます。

### 既存の案件に入れるとき

`/project-change` は、ウィザードなしで作った案件では最初に方針を聞きます。

- **既存ルール優先**: いまのルールと文書の書式を保ち、ウィザード標準と比べて足りない点だけを提案します。採ったものを、承認後に追記します。選んだモード・モデルの変更に必要な箇所は、別に差分を示して修正します。独自のルールが育っている案件向けです。
- **ウィザード標準優先**: 文書一式を導入します。いまのルールのうち持ち込めるものは `RULES.md` に入り、持ち込めないもの (一方の AI 専用のスキルなど) は `START.md` の「導入時の引継ぎ」に残して、最初のセッションで対応案を出させます。

どちらの方針でも、モードと各AIのモデル・effortを独立して選び、反映先は「既存フォルダを直接更新する」「案件全体を別フォルダへコピーして更新する」「ここで終わる」から選べます。全体コピーはコード・画像・docs・スキル・空フォルダも保持して、直接更新と同じ文書変更を適用します。コピー範囲は all (.env・鍵・.git・依存も含む全通常ファイル) / safe (それらとバックアップ・仮想環境を除外) を明示的に選びます。リンクはコピーせず承認前に一覧を示します。未作成・空の出力先を使え、非空は明示承認した --replace-output で旧出力全体を <出力先>.psw-backup/<日時>/ へ退避してから置換できます。

追記案を選ぶ質問は、複数選択のウィンドウが使えるなら複数選択、使えないなら本文付きの「採用する / 見送る」に分けます。案の採用、書き出し先の選択、書き込みの承認は区別します。

モードを選ぶと、役割分担もそのとおりに変わります (たとえば、いま両方の AI が実装している案件で `claude-led` を選ぶと、Claude は実装ファイルを直接編集しない決まりになります)。

## 使い方 (CLI)

```
node scripts/cli.mjs help
node scripts/cli.mjs questions --out my.setup.json          # 対話で質問 → yes で保存
node scripts/cli.mjs plan --config examples/config.example.json
node scripts/cli.mjs generate --config <設定> --out <新規フォルダ> --confirm <plan digest>

node scripts/cli.mjs apply --target <案件フォルダ>                                  # 現在の設定と文書の差分 (読むだけ)
node scripts/cli.mjs apply --target <案件フォルダ> --config <変更後設定>            # 変更した場合の差分 (読むだけ)
node scripts/cli.mjs apply --target <案件フォルダ> [--config <設定>] --confirm <確認用 digest>
node scripts/cli.mjs apply --target <ウィザードなしの案件> --config <設定> --adopt [--replace <名前,名前>] [--confirm <digest>]

node scripts/cli.mjs revise --target <案件フォルダ> --changes <変更案JSON> [--confirm <digest>]
node scripts/cli.mjs copy --target <案件フォルダ> --out <コピー先> --copy-scope <all|safe> [--changes <変更案JSON> | --config <設定> [--adopt] [--replace <名前,名前>]] [--replace-output] [--confirm <digest>]

node scripts/cli.mjs regenerate --config <設定> --from <案件フォルダ>               # 管理文書だけの比較用
node scripts/cli.mjs regenerate --config <設定> --from <案件フォルダ> --out <別の新規フォルダ> --confirm <確認用 digest> [--fresh]

node scripts/cli.mjs audit --target <案件フォルダ> [--report <新規ファイル>] [--json] [--unattended]
node scripts/cli.mjs gitignore --target <案件フォルダ> [--confirm <digest>]   # おすすめの .gitignore を、ないときだけ作る
node scripts/cli.mjs history --target <案件フォルダ>          # このツールがその案件に対して行った生成・更新の記録
node scripts/cli.mjs standard                                # ウィザード標準の要素の一覧
node scripts/cli.mjs update [--online] [--installed-version <版>] [--node-version <版>] [--unattended]
```

終了コード: `0` 正常 / `1` エラー / `2` 要確認 (必須の未回答、検出あり、無人で未決など)。

### 設定 JSON

`examples/config.example.json` を参照してください。

- 必須: `name` `purpose` `mvp` `mode`
- 任意: `outOfScope` `phases` `tech` `verifyCommands` `handoff` `permissions.allowedPaths` `permissions.forbidden` `gitignore` `profile` `pushPolicy` `launchPolicy` `uiRules` `layout` `projectRules` `handover` `notes` `ai.codex.model` `ai.codex.effort` `ai.claude.model` `ai.claude.effort` `ai.codex.fallbackModels` `ai.claude.fallbackModels`

モデル・effortは希望する起動設定として設定JSONとSTARTに保存します。空はクライアントの既定で、古い設定JSONにも対応します。稼働AIごとの手動起動例を案内しますが、現在のチャットやグローバル設定は変更せず、別AIは起動しません。利用できるモデル・effortはモデルとクライアントに依存します。

知らないキーや、API キー・トークン・パスワード・webhook らしい値は拒否します。任意の項目が空でも止まりません (未定として記録します)。

## 文書の配置

案件フォルダのルートには、各 AI の入口だけを置きます。

```
案件フォルダ/
├─ AGENTS.md / CLAUDE.md      各 AI の入口 (使う AI の分だけ)
├─ .gitignore                 おすすめの内容 (ないときだけ作る)
├─ docs/                      WORKFLOW.md、TASKS.md、VALIDATION.md、PROJECT.md、START.md など
└─ initial-settings/          setup.config.json (設定)、generated.manifest.json (記録と実行履歴)、backup/ (更新前のバックアップ)
```

- 仕様や設計の文書 (最初の課題 T-001 で案件側の AI が作るもの) も、同じ `docs/` に入ります。
- 以前の配置 (すべてルート) で生成した案件は、次の更新のときに新しい配置へ移せます。差分に「〜から移す」と出て、承認後に移します。書き足した課題表は中身を変えずに移し、元のファイルはバックアップへ移ります。
- ルートに置く配置のままにしたい場合は、設定で `"layout": "root"` にします。

## 運用の段階

生成する決まりの量を 3 段階から選べます (設定の `profile`。未指定は標準)。実運用で育った案件の決まりを、案件名や製品の内容を除いて一般化したものです。

| 段階 | 入るもの | 増える文書 |
| --- | --- | --- |
| 最小 `minimal` | 役割、承認、初期確認、検証の記録、再開メモ | — |
| 標準 `standard` | 最小に加えて、課題の個票 (`T-001`、6 項目)、着手中の印と完了処理の分担、レビューの記録と是正、ブランチとマージ、報告の書き方、指示ファイルと履歴の分離、ユーザー本人の作業 (`U-001`) と本人確認 (`UT-001`) | `CONTEXT.md`、`USER_TESTS.md` |
| しっかり `full` | 標準に加えて、検討から課題までの流れ、完了の記録と索引、公開・費用・引き継ぎの境界 | `BACKLOG.md` |

どの段階でも、最初の課題が「初期確認 → 基本ドキュメントを作る (`docs/` に仕様と設計の文書。足りない情報は AI があなたに聞く) → 必要な Skill を作る (文書をもとに、繰り返す手順をその案件の Skill にする) → MVP の最小の 1 経路」の順で入ります。文書と Skill を作るのは案件側の AI (最初のセッション) で、このツールは課題として置くだけです。標準以上では 6 項目の個票、最小では短い箇条書きになります。

`CONTEXT.md` は、その案件にしかない知識 (技術、フォルダ構成、開発コマンド、設計上の制約、規約) を書く場所です。ウィザードは欄だけを作り、中身は最初のセッションで AI が実在を確かめてから書きます。

## push の承認

設定の `pushPolicy` で選べます。

- `approval` (既定): push はそのつど、あなたの明示承認が要ります。
- `work-branch`: 課題を提出するときに、その課題の作業ブランチへは承認なしで push できます。`main` などほかのブランチへの push、マージ、公開は承認が要るままです。remote がなければ push しません。

## 別 AI の起動

設定の `launchPolicy` で選べます (引継ぎの `handoff` とは別の選択です)。

- `lead-launch` (協働モードの既定): 主導担当が、決めた範囲で実装担当を起動して課題を渡せます。1 回ごとの承認は要りません。範囲は、合格条件と確認事項が決まった課題の実装と、その差し戻しの修正だけです。公開、マージ、依存の追加、編集許可パス外の編集、費用を伴う操作は承認が要るままです。正本に「実装担当の起動」の節 (範囲、結果は自己確認として扱う、できない操作の肩代わりと記録、拒否を迂回しない、終了を確かめてから判定する) が入ります。
- `approval`: 別 AI の起動は、そのつどあなたの明示承認が要ります。AI を自分の手で 1 つずつ起動したい場合や、起動に費用がかかる場合はこちらにしてください。単独モードは常にこちらです。

既定のほうが、AI に任せる範囲が広い設定です。どちらになるかは、生成前の要約と `plan` の表示に必ず出ます。この項目ができる前に生成した案件 (設定に `launchPolicy` がない) は、文書が毎回承認のままです。何も指定せずに更新すると既定の `lead-launch` に変わるので (差分に出ます)、毎回承認のままにしたいときは設定に `"launchPolicy": "approval"` と書いてください。このツール自身は、どちらの設定でも別 AI を起動しません。

## モデルの代わりの順番

設定の `ai.codex.fallbackModels` / `ai.claude.fallbackModels` に、指定のモデルが使えないとき (混雑・非対応) の代わりを順番に書けます。`START.md` に順番つきで出ます。代わりを使ったら実際のモデルを記録に書く、代わりが書かれていなければ切り替える前にあなたに確かめる、という決まりも入ります。

## 画面の実装の基本

画面のある案件では、設定で `"uiRules": true` にすると、正本に「画面の実装の基本」の節が入ります (既定は入れません)。

- デザインはあなたと一緒に決め、決まったことをそのつど `docs/` のデザインルールの文書に書き足して正本にする (最初から文書を用意しない。決まっていないことを推測で書かない)
- 色・書体・余白などの値と表示文言を、画面のコードに直接書かない (入口を決めて通す)
- 画面は共通部品の組み合わせで作り、既存の部品を先に探す
- 直接書いた値や文言の検査を検証レシピに登録し、画面を変えたら状態・押せる範囲・拡大した文字を確かめる

## 更新後の対応 (課題表への追記)

`apply` (`/project-change` の直接更新とコピー) は、直せる文書 (正本、入口、`START.md` など) を直接更新します。それだけでは終わらない作業は、課題表 (`TASKS.md`) の末尾に「ウィザード更新後の対応」として書きます。

- 書くのは、今回の設定の変更にともなって案件側の AI が行うことです。例: 画面の決まりを入れた → デザインルールをあなたと決めて正本を作る、直接書いた値や文言を洗い出して移す、検査を検証レシピに登録する。別 AI の起動を変えた → 起動の手段と範囲を確かめて承認記録に書く。役割・モデル・push の承認・運用の段階を変えたときも、それぞれの対応を書きます。
- 書き足しがあって上書きしなかった作業文書 (`CONTEXT.md` など) のひな型が変わっていれば、「新しい欄のうち要るものを足す」も書きます。
- 既存の行は変えず、末尾に足すだけです。追記も差分と確認用 digest に含まれ、変更前の課題表はバックアップに残ります。同じ行は二度書きません。
- 課題の ID は振りません。案件の主導担当が読んで、必要なものを課題として発行します。
- ウィザードなしで作った案件への導入 (`--adopt`) と、既存ルール優先 (`revise`) では書きません。

## git と `.gitignore`

- **おすすめの `.gitignore` を、ないときだけ作ります。** 新規生成では最初から入り、既存の案件ではないときだけ足します。既にあれば、内容が何であっても触りません。中身は、秘密の入りやすいファイル、依存フォルダ、ログ、このツールのバックアップなどの一般的なものです。作りたくなければ、設定で `"gitignore": false` にします。
- **git を始めることを、最初のタスクにします。** `TASKS.md` の初期確認に「git 管理でなければ、`.gitignore` を確かめてから初期化し、最初のコミットを作る」が入ります。このツールは git のコマンドを実行しません。実行するのは最初のセッションの AI で、あなたの承認後です (push はしません)。
- 設定を持たない案件 (既存ルール優先) では、`node scripts/cli.mjs gitignore --target <案件フォルダ>` で同じ `.gitignore` を作れます。

## 実行履歴

`initial-settings/generated.manifest.json` の `history` に、このツールがその案件に対して行った操作を 1 回ごとに記録します: 日時、操作 (新規生成 / 更新 / 導入 / 別フォルダへ生成)、ツールの版、テンプレートの版、モード、書いたファイル、退避したファイル、残したファイル。あとから「どの版で何を作ったか」を追えます。

- 記録するのは案件内のファイル名だけで、絶対パスや設定の中身は入りません。
- 案件を git で管理しているなら、`initial-settings/` の `generated.manifest.json` と `setup.config.json` はコミットしてください (履歴ごと共有できます)。無視してよいのはバックアップ (`initial-settings/backup/`) だけで、これは自動で無視されます。
- 見るには `node scripts/cli.mjs history --target <案件フォルダ>`。

## 安全のための決まり

- **承認前に書き出しません。** 生成・更新・導入は、表示した digest と一致するときだけ実行します。確認のあとで設定や対象が変わると、古い承認は使えません。
- **既存を黙って上書きしません。** 新規生成は未作成または空のフォルダに限ります。全体コピーの非空出力は明示した --replace-output と承認digestでのみ、旧フォルダ全体を退避して置換します。隠しファイルやサブフォルダが 1 つでもあれば停止し、中身を削除して空にすることはありません。生成中に出力先の状態が変わっても停止します。更新は変更前を案件フォルダの `initial-settings/backup/<日時>/` に残します (git には出ないよう自動で無視されます。以前の配置ではルートの `.psw-backup/`)。書き足された `TASKS.md` / `VALIDATION.md` は上書きしません。
- **意味を読んで更新するのは管理文書だけです。** 全体コピーでは明示的に選ばれた範囲のコード等を解釈せず複製・ハッシュ確認します。allの場合の秘密・Git・依存の複製も同じ扱いです。内容を報告せず、リンクは辿りません。
- **入力は指示として扱いません。** 自由文は引用として保存します。ただし、引用による分離はプロンプト注入を完全には防げません。
- **検証コマンドは実行しません。** 保存するだけです。生成された文書でも、入力したコマンドは「実在未確認の候補」で、担当の AI が実在を確認して検証レシピに登録するまで、承認なしには実行されない決まりです。
- **ネットワークを使うのは `update --online` だけです。** 読むのは Claude Code 公式ドキュメントの 3 ページだけです。
- 秘密らしい値はパターンで検出して拒否しますが、検出は完全ではありません。

## 既知の制限

- **モデルとeffortの起動動作は未検証です。** CLIの構文は [Codex公式](https://learn.chatgpt.com/docs/config-file/config-reference) と [Claude公式](https://code.claude.com/docs/en/model-config) を参照しましたが、対象クライアントでAIを起動して確認していません。未知のモデルの対応可否は自動判定しません。
- **全体コピーは通常ファイルの内容と配置を保持します。** リンク・特殊ファイルは除外し、OSのアクセス権やタイムスタンプを完全再現するものではありません。クラウドや端末外の依存先の複製・接続検証もしません。

- **主導担当による別 AI の起動 (`launchPolicy: lead-launch`。協働モードの既定) は、文書の生成だけを確かめています。** 生成した決まりで AI が別の AI を起動して回した実績は、取り込み元の 1 案件の運用だけです。起動の手段 (コマンドやプラグイン) はこのツールでは決めず、案件の初期確認で決めます。
- **モデルの代わりの順番と画面の実装の基本は、決まりの文章を入れるだけです。** 代わりのモデルへの切り替えや、直接書いた値の検査を、このツールが行ったり確かめたりはしません。
- **更新後の対応は、設定の変更から決まる定型の文です。** 案件の中身 (コードや画面) は見ていないので、その案件で本当に要る作業かどうかは、案件側の AI とあなたが判断します。変更前の設定が読めない案件では書きません。
- **AI が実際に文書どおり動くかは確かめていません。** テストが確かめているのは、文書の構造と整合、保存と承認の仕組みです。入口の指示どおりの順に読むか、初期確認が 1 回で済むか、といった実際のセッションでの挙動は未確認です。
- **独立したレビューを受けていません。** 実装とテストは同じ担当が行いました。
- **Windows 11 と Node 22 でしか動かしていません。** macOS / Linux は未確認です。
- **日本語で使うためのツールです。** 生成する文書、Skill の手順、質問、CLI のメッセージは日本語だけです。英語などほかの言語では動作を確認しておらず、英語のテンプレートもありません。
- **標準としっかりの決まりは、2 つの案件の運用から一般化したものです。** その 2 件ではうまく回っていますが、生成した文書で新しい案件を回した実績はまだありません。課題の ID は、どの段階でも `T-001` の形です。
- **役割は 4 モードだけです。** 両方の AI が実装もレビューもする、といった分担は表せません。そういう案件に導入すると、選んだモードのとおりに運用が変わります。
- **既存ルール優先の判定は、Skill を実行する AI の読み取りによります。** 機械的な検査ではなく、読むのは案件フォルダ直下の管理文書だけです。
- **既存ルール優先の文書案はAIが作り、revise / copyが承認・バックアップ付きで反映します。** 案の意味の適切さはAIの読取に依存します。全体コピーのバイト一致・直接更新との同等性・確認後の変更拒否・退避と復元はtemp案件で検証します。
- **残した既存の文書とのつなぎ目は検査できません。** たとえば、既存の課題表を残して導入すると、正本が言及する初期確認の欄がその課題表にない、という状態を診断は検出しません。「導入時の引継ぎ」で最初のセッションに対応させてください。
- **Codexで既存ルール優先の全体コピーを1案件で確認しました。** 11,039通常ファイル・959フォルダの配置と内容、承認した文書変更、元案件の完全不変、旧出力と変更前文書の退避を確認しました。Codex用入口の同期は機械試験あり。他のモード・Claude Codeでの実セッション・すべての案件での挙動は未確認です。
- **Skill はこのフォルダで開いた AI から使います。** 別の場所から呼ぶ使い方には対応していません。
- CLI の対話 (`questions`) は、案件固有のルールと導入時の引継ぎを聞きません (設定 JSON で指定します)。
